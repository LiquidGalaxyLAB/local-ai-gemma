# VM Earth Startup Pitfall

## Problem

On VM rigs (VirtualBox, single or multiple VMs), the autostart chain `lg.desktop → launch-earth.sh → lg-run killall → ssh to all frames` hangs on SSH to unreachable or slow-to-boot slave VMs (lg2/lg3). This blocks Earth from ever starting on the affected machine.

**Why it happens:**
- `launch-earth.sh` runs `lg-run killall run-earth-bin.sh googleearth-bin` which calls `/home/lg/bin/lg-run`
- `lg-run` uses `ssh` to reach every frame in `$LG_FRAMES`
- On VM rigs, the internal network uses `10.42.69.x` — if a slave VM hasn't booted yet or Earth isn't responding, `ssh` hangs indefinitely
- The `-tt -x` flag in the SSH invocation prevents timeout-based fallback

**Symptoms:**
```
ps aux | grep ssh | grep lg@lg2
# → ssh -tt -x lg@lg2  killall run-earth-bin.sh googleearth-bin   (hung)
```
- `pgrep googleearth-bin` returns nothing
- `cat /home/lg/earth-start.log` shows "Google Earth appears to be running already" or is empty

## Root Cause — Stale Lock File

When Earth is killed uncleanly (power loss, `kill -9`, VM snapshot rollback), `/home/lg/.googleearth/instance-running-lock` is left pointing to a non-existent PID. Earth's launcher script refuses to start a new instance while the lock exists.

```
ls -la /home/lg/.googleearth/instance-running-lock
# → lrwxrwxrwx 1 lg lg 10 ... /home/lg/.googleearth/instance-running-lock -> /proc/1902
# (PID 1902 does not exist — stale lock)
```

## Rescue Procedure (Nara-Authorised Only)

The autostart approach is irrecoverable without a power cycle. When Nara explicitly authorises a direct start:

```bash
# 1. Kill the stuck SSH/lg-run processes that are blocking Earth
# Use the exact PID from ps, NOT pkill -f (which can kill your own SSH session)
sshpass -p 'lg' ssh lg@<IP> "kill <pid_of_launch-earth> <pid_of_ssh_to_lg2>"

# 2. Remove the stale lock file
sshpass -p 'lg' ssh lg@<IP> "rm -f /home/lg/.googleearth/instance-running-lock"

# 3. Verify X server is running (should show X0)
sshpass -p 'lg' ssh lg@<IP> "ls /tmp/.X11-unix/"

# 4. Start Earth directly, bypassing the launch script entirely
sshpass -p 'lg' ssh -f lg@<IP> \
  "nohup /opt/google/earth/pro/googleearth > /home/lg/earth-start.log 2>&1"

# 5. Verify after 20-30 seconds
sshpass -p 'lg' ssh lg@<IP> "pgrep -a googleearth-bin"
# Expected: <PID> /opt/google/earth/pro/googleearth-bin

# 6. Check window is visible
sshpass -p 'lg' ssh lg@<IP> \
  "DISPLAY=:0 xdotool search --name 'Google Earth Pro' getwindowname"
# Expected: "Google Earth Pro"
```

**The `ssh -f` flag is critical** — it backgrounds the SSH session, preventing the `nohup` process from being tied to the SSH session lifecycle. Do NOT use `&` or `disown` instead.

## Dismissing the Options Dialog

On first launch, Earth may show a "Google Earth Options" dialog blocking the main window:

```bash
sshpass -p 'lg' ssh lg@<IP> \
  "DISPLAY=:0 xdotool search --name 'Google Earth Options' key alt+a"
sleep 1
sshpass -p 'lg' ssh lg@<IP> \
  "DISPLAY=:0 xdotool search --name 'Google Earth Options' key Return"
```

## Verification — ViewSync Working

After Earth is running on all frames, confirm ViewSync is configured:

```bash
# Check drivers.ini (generated by write-drivers-ini.sh at Earth launch)
ssh lg@<lg1> "grep -A2 'ViewSync' ~/earth/builds/latest/drivers.ini"
# Expected: lg1 = send:true, lg2/lg3 = receive:true with correct yawOffsets
```

On a 3-screen VM rig:
- **lg1** (master): `ViewSync/send = true`, `yawOffset = 0`
- **lg2** (left): `ViewSync/send = false`, `yawOffset = -36.5`
- **lg3** (right): `ViewSync/send = false`, `yawOffset = 36.5`

All machines use broadcast address `10.42.69.255:45678`.

## Prevention

No full fix — the autostart `launch-earth.sh` is designed for physical hardware where all frames are always reachable. On VMs:
- After a power cycle, Earth never auto-starts correctly
- The rescue procedure above must be run for each slave VM that hangs
- A startup script that skips unreachable frames (timeout-based) could fix this but hasn't been implemented
